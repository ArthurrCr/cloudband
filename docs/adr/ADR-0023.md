# ADR-0023 — Fair comparison protocol between OCM and Swin+UPerNet

- **Status:** accepted
- **Date:** set at repository creation
- **Context:** notes 2.2 and 2.12 · OCM protocol (S2.2, S2.11) and STUPmask protocol (S3.2)
- **Supersedes:** the original formulation of note 2.12 ("inherit multi-resolution training
  from OCM")

---

## Context

Phase 2 compares a CNN (OCM ensemble) against a transformer (Swin+UPerNet), both restricted
to the same three bands, under "the same protocol." Two findings from the source papers show
that "the same protocol" is not directly executable as stated:

1. OCM's multi-resolution training spans 9 m to 50 m, 565x565 to 102x102 px, and the paper
   justifies this by the ability of CNN-based models to process arbitrary input sizes. A
   4-stage Swin at 102x102 reaches the final stage with a feature map of roughly 3x3, smaller
   than the 7x7 attention window. The technique is not architecture-neutral.
2. OCM uses an initial learning rate of 0.005 with fastai's `fine_tune`. That is a
   CNN-typical rate, an order of magnitude above what is usual for transformers with AdamW.

Applying both settings literally to both models would produce identical treatment and a
biased comparison.

## Decision

### D1 — Multi-resolution range: 9 m to 22 m, identical for both architectures

Derived, not an arbitrary choice. The p509 patch covers 5090 m, so `N = 5090 / gsd`:

| GSD | N (px) | stage-4 map (N/32) | viable for Swin-T (window 7) |
|---|---|---|---|
| 9 m | 565 | 17 | yes |
| 10 m | 509 | 15 | yes |
| 15 m | 339 | 10 | yes |
| **22 m** | **231** | **7** | **yes, limit** |
| 30 m | 170 | 5 | degenerate |
| 50 m | 102 | 3 | not viable |

22 m is the coarsest GSD at which the patch still yields at least 224 px, the minimum for the
final stage of a 4-stage Swin-T to keep a map of at least 7x7 without collapsing window
attention. The 9 m lower bound is inherited from OCM, to avoid undersampling the native 10 m.

The mechanism is preserved — the model still sees clouds at varying scales — while the range
where the technique stops being architecture-neutral is removed.

### D2 — Architecture-coupled hyperparameters: searched per model, with symmetric budget

That two architectures land on different optima is trivial. What decides the validity of the
comparison is which hyperparameters are allowed to differ, and how much search budget each
architecture gets to reach its optimum. Freeing everything is as biased as fixing everything —
it only flips the direction. Much of the advantage reported for new architectures in the
literature disappears once the baseline receives an equivalent search budget.

Explicit partition:

| Category | Items | Regime |
|---|---|---|
| Coupled to architecture | learning rate | searched per model |
| Defines task, data and budget | data, bands, splits, loss, augmentations and their probabilities, scheduler shape including warmup, epochs, effective batch, checkpoint criterion, weight decay, evaluation | fixed for both |

**Warmup is resolved and stays in the shared protocol.** The premise that STUPmask uses
warmup and OCM does not is false. OCM trains with fastai's `fine_tune`, which applies the
one-cycle policy: the rate rises from a low value to the maximum before decaying, so warmup
already exists, inherited from the scheduler rather than named explicitly. Both papers use the
same scheduler shape.

Removing warmup from Swin is also not a conservative choice: the original Swin paper uses 20
epochs of linear warmup, and follow-up work reports that Swin fails to converge without it,
tested with both Kaiming and truncated normal initialization. Other work reports base models
stalling without warmup.

Both architectures therefore use the same scheduler, rise followed by decay. Only the learning
rate value stays coupled to architecture. This is more defensible than the alternative: rather
than granting the transformer a resource denied to the CNN, the scheduler is identical and only
the operating point differs.

Caveat: the non-convergence evidence comes from training from scratch on ImageNet. Here, both
models start from ImageNet weights, a regime where warmup matters less. The cost of keeping it
is zero, so it is kept.

**Budget symmetry is what actually guarantees fairness:**

- same log-spaced learning rate grid, e.g. `{5e-5, 1e-4, 5e-4, 1e-3, 5e-3}`
- same number of runs per architecture — this is the item that prevents a reversed bias
- same selection criterion: lowest cross-entropy loss on the validation split (535 patches)
- grid and budget declared before running, so the search does not stop once the desired
  result appears

**The search never touches the test split (975 scenes).** Tuning the learning rate against
the test set turns the comparison into an overfitting result and also invalidates the paired
Wilcoxon test from note 2.10.

**Cost, and how to control it.** A full OCM run takes about 25 h (paper, S2.11). A grid of 5
points times 2 architectures times 3 variants is not feasible. Standard, defensible strategy:
select the learning rate with shortened proxy runs (e.g. 10 frozen epochs plus 10 unfrozen
epochs, one fifth of the full budget), then train the winner with the full budget. The
shortening must be identical for both architectures, otherwise it becomes another asymmetry.

Record in the manifest both full grids, both winners, and the validation curves of every proxy
run. The dissertation states: identical protocol except for architecture-coupled
hyperparameters, selected per model over the same grid, with the same number of runs and the
same criterion; fixing a single value would systematically penalize the transformer, and
freeing the search without budget symmetry would penalize the baseline.

### D3 — Two OCM variants, not one

The 9-22 m range diverges from the published OCM range (9-50 m). Since the fidelity check
requires the original protocol and the controlled comparison requires the shared protocol,
these are two different pieces of work and need two models:

| ID | Range | Learning rate | Role |
|---|---|---|---|
| `ocm-rgn-cs12-native` | 9-50 m | 0.005, from the paper | fidelity against the published BOA |
| `ocm-rgn-cs12-shared` | 9-22 m | searched, D2 | Phase 2, against Swin |
| `swin-rgn-cs12-shared` | 9-22 m | searched, D2 | Phase 2, against OCM |

Cost of the extra model: about 25 h of GPU per the paper. Cheap for what it buys — without it,
any discrepancy against the published value would be inexplicable, since there would be two
possible causes, an altered protocol or a wrong implementation, with no way to separate them.

### D4 — Symmetric pretrained initialization

OCM's backbones come from `timm` with ImageNet weights. Swin-T has equivalent ImageNet
weights. Both architectures start from ImageNet weights, or neither does. Since both use 3
channels, the RGB stem mapping is direct in both cases. Asymmetry here would be a larger
confound than anything in D1.

### D5 — What remains strictly identical

Data (CloudSEN12+, L1C and L2A of the same scenes), splits, the three bands, dynamic Z-score
normalization, loss (cross entropy), augmentations and their probabilities (image tear 10%,
random rectangle 60% with random fill, scene edge 10% without altering the label, rotations
and flips 100%), epoch budget, effective batch size, checkpoint selection criterion, seeds,
weight decay (single value, 0.01, same for both architectures — see item 4 below),
evaluation protocol.

### D6 — OCM backbones: the paper's, not the current package defaults

The package uses `regnety_004` and `edgenext_small` from version 2.0 onward, but the paper,
and therefore the protocol being reproduced, uses `regnety_004` and `convnextv2_nano`.
`ocm-rgn-cs12-shared` adopts the paper's backbones. See `docs/protocols/ocm_protocol.md`,
version history.

### D7 — Reporting: one controlled table, plus one labeled informative table

`ocm-rgn-cs12-shared` versus `swin-rgn-cs12-shared` is the only result presented as isolating
architecture; both are trained under D1-D6, so a difference between them is attributable to the
backbone.

A second table may additionally place `swin-rgn-cs12-shared` next to the published OCM weights
(`ocm-rgn-published-v1.7.0`, already scored by the phase 0 baseline notebooks, or the paper's
own `ocm-rgn-published-v1.0` numbers). This table exists for context, not as a second
architecture comparison, and its caption must say so explicitly: the published weights differ
from `swin-rgn-cs12-shared` in more than backbone alone — GSD range (9-50 m against 9-22 m) and
learning rate regime (fixed at 0.005 against searched, D2) both differ too. A gap in this table
is not evidence about architecture and must not be presented as such; the same caveat D3 already
attaches to `ocm-rgn-cs12-native` in place of a fidelity check.

## Consequences

**Positive.** The comparison isolates architecture. The native/shared distinction makes the
fidelity check interpretable. The range is derived from an explicit architectural constraint,
not preference, and is defensible in one sentence during the defense.

**Negative, to state in `docs/LIMITATIONS.md`.**

1. Landsat-8 falls outside the training range: 30 m exceeds 22 m, so evaluation on PixBox-L8
   becomes extrapolation for both models. This preserves fairness, since both extrapolate
   equally, but the absolute BOA values on L8 will sit below the published ones and are not
   comparable to OCM's Table A.2. Use `ocm-rgn-cs12-native` for an L8 number comparable to the
   literature.
2. `ocm-rgn-cs12-shared` is not OmniCloudMask. Never report its BOA as OCM's performance, the
   same rule note 2.2 already sets for STUPmask.
3. The learning rate search consumes GPU budget before the main training run.
4. The single weight decay value used for both architectures (D5) is 0.01, confirmed from two
   independent sources rather than assumed: STUPmask states AdamW with weight decay 0.01
   directly; the OmniCloudMask paper (Section 2.11) does not mention weight decay at all, but
   its public training notebook (`training/Train OCM models.ipynb` in the OmniCloudMask
   repository) constructs the fastai `Learner` and calls `fine_tune` without ever passing `wd`,
   so training falls back to fastai's `Adam` default of `wd=0.01` with decoupled weight decay.
   Both papers converge on the same value through different paths.

## Rejected alternatives

| Alternative | Why not |
|---|---|
| Full 9-50 m range for both | Swin degenerates below about 22 m; identical treatment, biased comparison |
| Multi-resolution for OCM only | reintroduces exactly the confound note 2.12 exists to eliminate |
| No multi-resolution for either | protocol identical, but OCM loses 0.6-1.2 pp of BOA (Table A.7, "Accuracy metrics of OCM trained at 10 m resolution and OCM trained with mixed resolutions on the Sentinel-2 PixBox test dataset," discussed in Section 3.3 and Figure 11 of Wright et al. 2025) and stops being the method from the paper |
| Reduce the Swin window to 4 or 5 | would allow 30 m, but stops being standard Swin-T and becomes another free variable |
| Use the p2000 tier, 20 km extent | would solve the geometric limit, but only 687 high-quality training patches are available, too few to train from scratch |
| Single learning rate for both | this is the central trap this ADR addresses: identical is not fair |
